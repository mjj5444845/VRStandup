第七个工作：模块边界检查（M1 E02）
更新：2026-10-30

一、这一步有什么用

不同部分的代码应该各管各的事：基础规则负责规则，三维部分负责画面，服务负责保存和通信。
如果基础规则偷偷用上画面或电脑文件功能，以后替换模型、换运行电脑就容易相互影响。
这一步让电脑自动找出不合规则的引用，专业上叫“依赖边界检查”。
检查不运行演员、不读取实验数据，也不需要连接 Quest 3。
它是 M1 的一项，不表示 M0 或整个 M1 已经验收。

二、准备条件

在 Mac 或 Windows 的项目根目录打开终端，按对应安装指南安装 Node.js 和项目依赖。
这一步没有新增工具包；使用项目已经固定版本的 TypeScript。
Mac 已实际运行。Windows 命令采用跨平台写法，仍待实验室电脑实测。

三、运行方法

Mac：
  npm run check:boundaries

Windows PowerShell：
  npm.cmd run check:boundaries

如果要运行全部代码检查和测试：
  Mac：npm run check
  Windows：npm.cmd run check

如果修改了程序，还要构建网页：
  Mac：npm run build
  Windows：npm.cmd run build

四、怎样判断成功

终端显示检查了多少源码文件、多少正式模块文件，以及“发现 0 个问题”。
本轮扫描 app/ 和 study/ 下 43 个源码文件，其中 2 个是正式入口占位页。
文件数量以后会变化；数量增加不表示功能通过验收。
发生违规时显示文件位置、行号、原因与被引用的路径，命令返回失败状态。
这会让 npm run check 停下来，避免把违规修改误认为通过。

例如，如果 study/core/rules.ts 引用了 study/xr/scene.ts，会提示 core 不能依赖这个三维文件。
解决方法是把通用规则放回 core，让 xr 调用 core；不要为了通过检查直接放宽规则。

五、当前允许的连接方向

core（基础规则）：只引用 core 内部代码。
xr（三维场景）：可以引用 xr、core 和 Three.js。
web（浏览器功能）：可以引用 web 和 core，使用浏览器自带的接口。
server（实验服务）：可以引用 server、core、Node.js 和 ws。
tools（离线整理）：可以引用 tools、core 和 Node.js。
app/study（参与者页面）：可以引用自己的页面代码、xr 和 web。
app/lab（控制台页面）：可以引用自己的页面代码、web 和 core。
页面可以使用 React、Next.js 和自己的样式。

正式模块不能引用 study/spikes/ 或 app/spike/ 中的技术试验代码。
新代码不能导入 archive/ 旧归档、local_assets/ 原始资料或 data/ 等本机私密目录。
测试文件可以使用 Node.js 自带测试工具，但运行代码不能反过来引用测试文件。
新增模块先说明职责，再同步修改规则、文档和正反测试；不要创建空目录占位。

六、检查能发现什么

普通导入、只导入类型、转发其他文件的导出、require 和动态 import。
实际 tsconfig.json 中的路径别名也会检查，不靠另一套别名猜测路径。
无法确定名称的动态导入会失败：依赖要写成固定字符串才能检查。
源码中的三斜线类型引用和符号链接会被拦住，避免绕过已登记的依赖方向。
文件不存在或本地路径无法解析也会失败。

检查范围是 app/ 和 study/ 当前源码的导入关系，不扫描旧工程或本机资料目录。
它不是安全沙箱，不检查所有 DOM 全局变量、运行时文件读取、网络地址或资源加载。
类型检查、素材来源登记、权限管理、Windows 和头显实测仍各有用途。
工具在 scripts/architecture/，属于开发工具，不会接入实验运行模块。

七、常见问题

1. 提示找不到 TypeScript 或 tsx：确认在项目根目录安装依赖，再运行 npm ci（Windows 用 npm.cmd ci）。
2. 提示本地依赖无法解析：检查文件是否存在、大小写、相对路径和项目别名。
3. 提示某层不能引用其他层：查看第五节，让使用者调用基础层，或把代码放到正确职责的模块。
4. 代码检查通过却无法进入 VR：两项检查目的不同，头显仍需要单独连接和验收。
5. Windows 结果：尚未实测，不能用 Mac 通过代替。
